# A2A Insightsの編集・執筆基準

## 読者と読後目標

記事ごとに主読者を1つ選び、補助読者を増やしすぎない。

| 主読者 | 前提知識 | 読後にできること |
| --- | --- | --- |
| 開発者・アーキテクト | API、認証、分散システムの基礎 | 仕様差分を理解し、実装や検証項目へ落とす |
| セキュリティ・運用担当 | 脅威分析、監査、運用管理の基礎 | リスクと責任境界を見極め、対策を選ぶ |
| 技術選定・事業責任者 | AIエージェントの概念 | 導入時期、比較軸、組織への影響を判断する |
| 投資家・市場観測者 | 市場と主要企業の基礎 | 技術変化と事業上の意味を分けて評価する |

執筆前の内部メモに次を書く。

```text
主読者:
前提知識:
この記事で答える問い:
読後にできること:
扱わない範囲:
```

このメモは本文へ貼り付けない。

## 記事種別ごとの流れ

OpenClawが作る標準記事の主要H2は4〜5個にする。末尾の`参照した一次情報`は主要H2数に含めない。既存の特殊な実測記事へこの制約を遡って適用しない。

### ニュース解説

1. 何が変わったか
2. 仕組み、対象範囲、従来との差
3. 開発・運用・市場への影響
4. 制約、未確認事項、今後確認する点
5. 読者が今取るべき行動

### 常設解説

1. 用語の定義と直接回答
2. なぜ必要か、似た仕組みとの違い
3. 構成要素と動作
4. 設計・導入の判断基準
5. 制約、リスク、チェックリスト

### 実測・定点観測

1. 結論と観測対象
2. 母数、取得方法、指標の定義
3. 結果
4. 解釈と実務上の意味
5. 対象外、再現条件、検証していない範囲

## タイトルと導入

- `title`は検索意図へ直接答え、テーマと読者の判断材料を示す。
- `shortTitle`はパンくずや前後ナビで意味が残る短さにする。
- `description`は記事で得られる答えと主要論点を1〜2文で示す。本文の結論と食い違わせない。
- 冒頭1〜3段落で、定義、結論、変更点のいずれかを明示する。
- 「本記事では解説します」「いかがでしたか」のような内容を持たない定型句で始めたり終えたりしない。

## 本文の書き方

- 専門用語は初出で短く定義する。
- 初心者向けでも条件、バージョン、例外、責任境界を省かない。
- 抽象的な評価語より、主体、動作、対象、条件を具体的に書く。
- 比較軸が複数ある場合は表を使う。
- 実装手順や時系列は番号付きリストを使う。
- 導入判断はチェックリストにする。
- SEO語を不自然に反復しない。
- 未提供機能、未検証の優位性、根拠のない将来予測を書かない。
- 「革新的」「非常に重要」「大きな可能性」のような評価は、何が誰にどう影響するかへ書き換える。

## 事実・解釈・未確認を分ける

次の状態を混ぜない。

- 確認済みの事実: 一次情報が直接述べていること
- 解釈: 複数の事実から導く実務上・市場上の意味
- 未確認: 公開情報から判断できないこと
- 将来計画: 提供者が発表した予定であり、提供済みではないこと

`GA`、`Preview`、`Beta`、`検討中`、`確認できず`などの状態語を必要に応じて明示する。推論を書く場合は「〜と考えられます」だけで曖昧にせず、根拠と推論の間を説明する。

## 情報源

- 公式仕様、公式ドキュメント、標準化団体、政府・公的機関、対象サービス自身の発表を優先する。
- 重要な主張の直後に、主張を直接支えるURLを置く。
- 仕様、UI、提供状況には対象バージョンと「YYYY年MM月時点」を書く。
- 末尾に`## 参照した一次情報`を置き、名称、提供元、URLを列挙する。
- 実測記事では、母数、取得方法、指標の定義、取得日、対象外、検証していない範囲を書く。
- 更新時は日付だけを変えず、本文と一次情報を再確認する。
- 二次記事だけを根拠に仕様やセキュリティ上の断定をしない。

## 公開文へ出さないもの

内部処理の追跡情報は読者向けの根拠ではない。次を本文へ出さない。

- Current Full KG、Judge PASS / NEEDS_FIX
- candidate_id、source_id、draft_sha256、内部ハッシュ、審査ラベル
- 根拠パック、抽出スコア、内部優先度
- エージェントへの指示、生成・校正の作業メモ

公開可能な一次情報、確認日、対象バージョン、検証方法へ置き換える。OAuth claim、JWT claim、SAML assertionなど、公開仕様そのものの正式用語は禁止しない。

## 画像

- 既存記事にならい、ネイビー、黒、白を基調にシアンまたはインディゴをアクセントにする。
- 一般的なロボット、脳、握手、過剰なネオン、意味のない回路図を主題にしない。
- 記事固有の関係、境界、流れ、観測対象を1つの焦点で表す。
- 根拠のない数値、架空の製品UI、ログ、企業ロゴを描かない。
- ラスター画像内へ細かい説明文を詰め込まない。正確なラベルが必要ならHTML、CSS、SVGなど検証可能な表現を検討する。
- altは「アイキャッチ画像」ではなく、伝わる関係や状況を具体的に書く。

## 最終レビュー

- 冒頭だけで記事の問いと答えが分かるか。
- 1つの主読者に必要な判断材料がそろっているか。
- タイトル、description、本文の結論が一致しているか。
- 重要な主張を一次情報が直接支えているか。
- 事実、解釈、未確認、予定を読み分けられるか。
- バージョン、情報基準日、母数、対象外が必要な箇所にあるか。
- 見出しだけを読んでも論理の流れが分かるか。
- 内部用語、AI的な定型句、重複説明を削除したか。
- 会社や製品への誘導を記事の論点へ無理に混ぜていないか。
- 画像が記事固有で、事実性とアクセシビリティを満たすか。
