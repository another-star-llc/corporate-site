AIエージェントが外部へ仕事を頼み、データや計算資源を買うための決済規格と製品が整いつつあります。その取引では、誰に頼むか、いくらまで払うか、届いた成果物が注文どおりかを判断しなければなりません。仕事が終わらなかったときには、やり直しや返金を求める相手も必要です。

Another Starは、企業が外部エージェントを探して仕事を任せ、成果を受け取るまでを支える製品を目指しています。決済サービスと連携し、依頼先の評価に加えて、注文や支払い、納品、返金の状況を一つのサービスで確認できるようにする構想です。

> 規格・製品の情報は2026年10月時点です。当社の決済連携・取引管理は構想段階で、将来の市場像や価格、仲介料10％は説明のための仮定です。

## エージェントが売買する未来

利用者が「競合3社を調べて、レポートにまとめてほしい」と指示し、そのエージェントが外部の調査エージェントへ仕事を依頼するとします。調査側も、企業データの取得、外国語資料の翻訳、分析に必要な計算資源を、それぞれ別の事業者から購入するかもしれません。

この例では、レポートを売るエージェントが、別の取引では買い手になります。一つの成果物を作る過程に、専門作業やデータ、計算資源を買う取引が重なっていきます。

A2AはAgent-to-Agent、つまりエージェント間のやり取りを指します。A2Aプロトコルは、依頼の伝達や、仕事の単位と進捗を表すTask、成果物を表すArtifactなどの扱いを共通化します。本稿でいう「A2A決済」は、こうした有料の仕事に購入の承認や支払いを結び付ける仕組みを指し、A2A本体が一つの決済手段を指定しているわけではありません。[A2A公式仕様](https://a2a-protocol.org/latest/specification/)

### 変わる依頼先と支出

この将来像では、人が目的や予算、求める品質を伝え、エージェントが条件に合う依頼先を探します。仕事の途中で依頼先を変えたり、別のエージェントに一部を任せたりすることもあるでしょう。そのたびに、残りの予算はいくらか、どこまで任せてよいか、仕事はどこまで進んだかを確かめることになります。

## 決済規格と市場の現在地

2026年10月時点では、購入承認、支払要求、商品・注文の交換を扱う複数の規格が公開され、StripeやAWSなどの製品による対応も進んでいます。ただし、規格ごとに共通化する対象が異なり、実際に代金を受け取れるかは、決済製品の提供地域、対応するカードやウォレット、口座の条件によって変わります。

支払いの承認を扱うAP2、決済処理につなぐx402やMPP、店舗の購入手続きを扱うUCPやACPは、それぞれ取引の一部を共通化する規格です。当社は接続先に合わせてこれらを使い、依頼先の評価や成果の確認、問題が起きたときの対応を製品として担う構想です。

複数のエージェントに仕事を任せるには、追加の管理も必要です。たとえばAP2 v0.2では、購入を代行するエージェントから別のエージェントへの承認の再委任は仕様の範囲外です。仕事を引き継ぐ際の予算や権限まで、既存規格だけで管理できるわけではありません。[AP2公式仕様](https://ap2-protocol.org/ap2/specification/)

### 決済サービスの利用条件

StripeのMachine paymentsでは、エージェントからのカード決済やステーブルコイン決済を受け付けられます。ステーブルコインは、米ドルなどの法定通貨への価値連動を目指す暗号資産です。事業として見ると、どの規格を使うかに加えて、一件いくらの仕事を、誰に販売できるかが問題になります。[Stripe Machine payments](https://docs.stripe.com/payments/machine)

<div class="blog-table-wrap" tabindex="0" role="region" aria-label="決済サービスの条件と事業への影響。横にスクロールできます">

| 利用条件 | 事業への影響 |
| --- | --- |
| Stripeの機械向けカード決済は最低0.50ドル | それ未満の仕事を一件ずつ決済する用途には使えない |
| ステーブルコイン決済は最低0.01 USDC。MPP sessionsは1セント未満の利用を計量し、最低0.01 USDCで精算 | 少額のデータ利用などをまとめて精算する設計が可能 |
| 提供地域や利用資格は製品ごとに異なる | 想定する買い手と提供事業者が利用できる経路を選ぶ |

</div>

10ドルのレポートと、1回0.001ドルのデータ利用では、適した支払経路が変わります。後者を1,000回利用して合計1ドルで精算する設計なら、データを取得するたびに送金する必要はありません。少額取引では、利用のたびに記録を残しつつ、送金をまとめる設計が採算に関わります。

日本からの利用には、製品ごとの地域制限があります。カード決済とステーブルコイン決済では受付条件が異なるため、想定する買い手と提供事業者が使える経路を確認します。

- カード決済に使うSPT（Shared Payment Token）は、利用条件や期限を設定できる支払い用トークンです。公開対象国一覧に日本は掲載されていません。[SPTの提供地域](https://docs.stripe.com/agentic-commerce/concepts/shared-payment-tokens.md?agent-seller=seller)
- ステーブルコイン決済については、Stripeが米国外の30以上の国で受付の利用申請を案内しています。日本事業者が承認されるかは個別確認が必要です。[Machine paymentsの条件](https://docs.stripe.com/payments/machine)
- Link Agent Walletで支払える顧客は米国・カナダが対象です。販売者の所在は問いません。[Link Agent Wallet](https://docs.stripe.com/agentic-commerce/agents/link-agent-wallet)

</details>

AWSも、外部サービスへの支払いを支援するAmazon Bedrock AgentCore paymentsを2026年8月18日に一般提供し、x402とMPPに対応しています。決済サービスを利用する選択肢は増えていますが、支払いの結果と、依頼した仕事が完了したかどうかは、それぞれ確認する必要があります。[AWS一般提供発表](https://aws.amazon.com/about-aws/whats-new/2026/08/bedrock-agentcore-payments-ga/)

支払いを実行できる製品は登場していますが、独立した買い手が継続して仕事を購入する市場の大きさや、仲介事業の採算までは、こうした数字から判断できません。

## 取引を支える管理機能

利用者が承認した10ドルを正しい相手へ支払えても、調査レポートが届かなければ依頼は完了しません。届いたレポートに必要な出典や調査対象が欠けていれば、合意した条件を満たしているかどうかの確認や、修正の依頼も必要になります。

支払いの完了と仕事の完了は、別々に扱います。A2A x402拡張でも、支払いが済んだ後に成果物の生成が続く場合を想定しています。署名を検証できても、レポートの品質まで保証されるわけではありません。[A2A x402拡張仕様v0.1](https://github.com/google-agentic-commerce/a2a-x402/blob/main/spec/v0.1/spec.md)

### 納品・支払い・返金の管理

売上の配分や返金には、Stripe Connectなど既存の決済製品を利用できます。ただし、どの注文にいくら配分するか、成果が条件を満たさなければ誰が費用を負担するかは、仲介サービス側で決めます。顧客への返金だけで、事業者に渡した資金や仲介料まで自動的に戻るとは限りません。

<details class="payment-note">
<summary>補足：売上配分と返金の仕組み</summary>

- Stripe Connectには、仲介料を受け取る機能や事業者への送金機能があります。[Connectの仲介料](https://docs.stripe.com/connect/marketplace/tasks/app-fees)
- Tempo chargeの仕様には、同じ通貨トークンを複数の宛先へ一括で配分する仕組みがあります。全員への送金をまとめて成功または失敗させますが、MPPのすべての支払方式に共通する機能ではありません。[Tempo Charge draft](https://paymentauth.org/draft-tempo-charge-00.html)
- Stripeでは、顧客に返金しても仲介料に当たるapplication feeは既定で自動返還されず、事業者へ配分した資金も自動的には戻りません。顧客への返金、事業者分の回収、仲介料の返還をそれぞれ管理します。[Connectの返金・紛争処理](https://docs.stripe.com/connect/marketplace/tasks/refunds-disputes)

</details>

こうした管理は、決済事業者の機能と利用企業自身のシステムを組み合わせても実装できます。当社は、依頼先を探すところから成果と支払いを確認するところまでを引き受け、利用企業の手間を減らしたいと考えています。特に、納品されない、支払いの結果が分からないといった場面で、企業自身が調べて対応する負担をどこまで減らせるかを検証します。

### 同時発注と再委任のリスク

たとえば、二つのエージェントが同じ10ドルの残高を見て、それぞれ6ドルの仕事を発注すると、合計は12ドルになります。個々の支払いを確認するだけでは、こうした予算超過を防げません。再委任や仕事の分岐が加わると、管理する対象はさらに増えます。

## Another Starの製品構想

Another Starは、依頼先を紹介した後も、納品や支払いの確認、問題が起きたときの対応まで引き受ける構想です。[製品ページ](/product)で示しているエージェントの審査や信頼スコア、仲介実行、異常検知を、実際の有償取引の管理へ広げていきます。

利用者には、予算の範囲内で仕事を任せ、成果と支出を確認できるサービスを届けたいと考えています。提供事業者にとっても、自社のエージェントを見つけてもらい、何を納品すればいくら受け取れるのか、問題が起きたらどう対応するのかが分かる仕組みを目指します。

<details class="payment-note">
<summary>補足：二重送金や処理の失敗に備える実装</summary>

候補となるのは、次のような仕組みです。

- **処理の抜けを防ぐ：** 状態の更新と送信予定を一緒に保存するTransactional Outbox。[AWSの解説](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)
- **再送を識別する：** 同じ操作の再実行だと識別できる冪等性キー。[Stripeの解説](https://docs.stripe.com/api/idempotent_requests)
- **失敗後に取り消す：** 完了した処理を、取消や返金などの別処理で補うSaga。[AWSの解説](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)

これらを使っても、外部の決済処理が必ず一度だけ実行されることや、すべての取消・返金が成功することは保証できません。処理結果の照合と、未解決の取引を追跡する運用も必要です。

</details>

資金を保留できるか、いつ事業者へ配分するか、返金できるかは、接続する決済サービスの条件に合わせて設計します。自社システムで予算を予約するだけでは、利用者の資金を確保したことにはなりません。[Stripeの支払枠確保](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method)

## 事業化に向けた検証

事業として成り立つには、利用者が繰り返し仕事を買い、提供事業者が仲介料を払ってでも参加を続け、その収入で当社の運用費用を賄えることが必要です。購入後にもう一度使われるか、直接依頼するより手間が減ったか、一件の取引にいくらかかったかを確かめていきます。

### 需要・顧客価値・採算

<div class="blog-table-wrap" tabindex="0" role="region" aria-label="仲介事業の仮説と検証項目。横にスクロールできます">

| 検証する仮説 | 確認すること |
| --- | --- |
| 外部の仕事を買う需要がある | どの仕事に実際の支払いが発生し、同じ利用者が再購入するか |
| 選定・評価が役に立つ | 相手探しや条件調整の手間、品質条件を満たさない納品を減らせるか |
| 取引管理の支援に料金を払う理由がある | 直接接続と比べ、支払・検収・失敗対応の負担が減るか |
| 提供事業者が参加を続ける | 受注と運用負担を踏まえて、仲介料を受け入れられるか |
| 取引ごとの採算が合う | 仲介料から決済・評価・監視・返金・人の対応費用を引いて利益が残るか |
| 人の承認を減らしても支出と取引を管理できる | 予算超過、二重課金、未照合入金、未精算額を抑えられるか |

</div>

仲介料10％の例なら、10ドルの取引から得る1ドルの範囲で、こうした費用を賄えるかを確かめます。小口取引では、交渉や検収のたびに人が対応すると、仲介料を対応費用が上回りかねません。複数回の利用をまとめて精算する方法や成果確認の自動化が有効か、どの仕事に人の判断を残すべきかも、商品ごとに検証する必要があります。

### 取引を広げる条件

初期の検証では、事業者・商品・支払経路を限定し、一件の注文について、代金の受領、売上配分、納品、検収、必要時の返金まで確認することを想定しています。実際の買い手が利用できるカードやウォレットを起点に、必要な規格を選びます。この範囲で継続購入の有無と、一件あたりの対応時間・費用を測ります。

複数社への発注や従量利用へ進む際には、元の依頼と再委任先の仕事の対応、利用量、相手ごとの支出上限、一部の仕事だけが失敗した場合の対応を確認します。さらに多段委任へ広げるには、元の権限と予算が引き継がれ、取引が分岐・変更されても、問題が起きた際にどこまで停止し、誰が費用を負担するかを把握できることが条件になります。

Another Starが目指すのは、企業が外部エージェントへ仕事を任せ、注文した成果を受け取れるサービスです。相手を紹介した後も、納品や支払いを追い、仕事が止まったときには対応できるようにしたい。その支援が継続して選ばれ、仲介料を払う理由になるかを、実際の有償取引で確かめていきます。
